# 0.2.2 — Deterministic browser security acceptance hotfix

## Root cause

The 0.2.1 Windows `FULL-ACCEPTANCE` correctly reached the production UI under strict CSP, but the live XSS assertion incorrectly required the real generative model to echo an exact hostile HTML string. A real model is stochastic and is not a deterministic fixture, so the test could fail even when the UI safely rendered every returned string.

## Corrected test architecture

`FULL-ACCEPTANCE` now separates two independent concerns:

1. **Real-runtime browser journey** — production Personal Agent Rus + the real local provider/model. It proves real chat, all user modes, mobile chat, admin login/routing/pull, persistence, strict CSP, and deterministic safety of USER-origin hostile HTML. It never requires an exact LLM phrase.
2. **Deterministic browser-security journey** — an isolated Docker network containing the exact production Core image plus a controlled fake provider. The provider returns exact hostile assistant content and a hostile model name. A real Playwright browser loads the real HTTP Core with the production CSP and proves the strings remain text and never become executable DOM.

The deterministic fixture is temporary, has no published port, does not use the production data/model volumes, and is removed after the test.

## Test hygiene

The Admin journey snapshots the owner's routing before mutation, verifies save + reload persistence, then restores the original routing and verifies the restoration. Acceptance must not leave test configuration behind.

## Regression rules

- Production CSP must not add `unsafe-eval`.
- Live browser tests must not use `wait_for_function` or JavaScript `eval`.
- Real-model acceptance must not depend on an exact generated response.
- Exact malicious assistant/admin payload assertions belong to deterministic fixtures.
- The Windows full gate must include both the real-model and deterministic-security browser journeys.
