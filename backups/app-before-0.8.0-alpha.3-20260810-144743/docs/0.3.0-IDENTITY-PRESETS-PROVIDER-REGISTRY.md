# Personal Agent Rus v0.3.0 — Identity, Presets and Provider Registry

Status: IMPLEMENTATION CONTRACT

## Goal

Replace three prototype shortcuts before Web/Files/Code are enabled:

1. USER starter cards become structured presets, not text snippets.
2. Local and external AI backends are represented by a Provider Registry with automatic model discovery.
3. Account/registration flows exist as a formal product surface for multi-user/server deployment while local personal mode remains supported.

## Product invariants

- USER never selects or sees raw model/provider IDs.
- ADMIN never has to manually re-enter a model ID that a provider can discover.
- A route is `(provider_id, model_id)`, never only a model string.
- Provider discovery is authoritative for inventory/availability.
- Bootstrap model is only smoke/fallback, not a product routing decision.
- External provider credentials never appear in USER APIs, HTML, logs, diagnostics or release evidence.
- Preset changes intent/instructions; it does not silently disable capabilities.

## Structured presets

Canonical presets:

| ID | UI | Contract |
|---|---|---|
| `explain` | Объяснить | Explain clearly, adapt complexity, examples when useful. |
| `write` | Написать | Produce a usable draft/plan/text according to request. |
| `analyze` | Проанализировать | Compare evidence/options, state criteria and conclusion. |
| `none` | Обычный чат | No extra task-specific instruction. |

Request shape:

```json
{
  "mode": "smart",
  "preset": "analyze",
  "messages": [{"role":"user","content":"..."}]
}
```

Preset and mode are independent:

```text
mode      = effort / performance profile
preset    = user intent helper
capability= chat/web/files/code/...
```

Language retry must preserve preset, mode and capability context.

## Provider Registry

### Provider types in v0.3 foundation

- `ollama`
- `openai_compatible`

Future adapters can add LM Studio/llama.cpp as explicit aliases/profiles, while retaining OpenAI-compatible transport when applicable.

### Local Ollama

`local-ollama` is system-managed and created automatically.

Discovery:

```text
GET /api/tags
```

Every installed model returned by Ollama appears in unified inventory automatically.

### OpenAI-compatible provider

Admin configures a connection once:

```text
name
base_url
api_key (optional)
enabled
```

Discovery:

```text
GET <base_url>/models
Authorization: Bearer <secret>   # when configured
```

Inference:

```text
POST <base_url>/chat/completions
```

Manual model ID entry is only a fallback for providers where discovery is intentionally unavailable.

### Unified inventory

Each entry contains at least:

```json
{
  "provider_id": "local-ollama",
  "provider_name": "Локальный Ollama",
  "provider_type": "ollama",
  "model_id": "qwen3:8b",
  "display_name": "qwen3:8b",
  "available": true,
  "source": "discovery"
}
```

USER API MUST NOT expose this inventory.

### Routing

Routing row:

```text
mode
provider_id
model_id
updated_at
```

Admin chooses from discovered inventory.

If configured route becomes unavailable:

```text
configured route unavailable
→ evaluate configured fallbacks
→ bootstrap local route if allowed
→ otherwise controlled product-level error
```

No hidden remote fallback when privacy policy is `LOCAL_ONLY`.

## Provider secrets

For the Docker prototype, secret values are written only to a dedicated `/data/secrets` store with restrictive file permissions. DB stores only a secret reference.

Server/VPS hardening must support a stronger external secret backend without changing Provider Registry API.

Secrets are redacted from:

- API responses;
- audit details;
- logs;
- diagnostics bundles;
- browser storage.

## Identity / registration modes

Two deployment modes:

### Personal/local

Single owner; registration is not required to start using localhost.

### Accounts/server

Registration/login/session is required.

Required routes:

```text
/register
/login
/logout
/account
```

Required security:

- PBKDF2/Argon2-quality password hashing;
- random session tokens;
- HttpOnly cookie;
- SameSite policy;
- session expiry/revocation;
- no password/token in logs;
- per-user data boundary.

Self-registration policy is ADMIN-controlled:

```text
open
approval_required
closed
```

## Admin UX

Admin navigation becomes:

```text
Обзор
Провайдеры
Модели
Маршрутизация
Пользователи
Система
```

### Providers

- system local Ollama shown as discovered/healthy/unhealthy;
- add OpenAI-compatible connection;
- test connection;
- refresh discovery;
- disable connection;
- remove user-created connection.

### Models

Inventory is grouped by provider. No primary workflow asks for a raw model ID.

`Скачать модель` exists only for providers that support managed pull (e.g. Ollama).

### Routing

Select options are inventory records:

```text
[Локальный Ollama] qwen3:8b
[LM Studio] model-x
[Remote Provider] model-y
```

## Acceptance

Mandatory:

- existing Ollama models discovered automatically;
- newly pulled Ollama model appears without manual registration;
- OpenAI-compatible provider can be created/tested/discovered;
- provider secret not returned by APIs;
- USER system endpoint contains no provider/model IDs;
- route persists as provider+model after restart;
- unavailable route produces deterministic fallback/error;
- structured `explain/write/analyze` preset reaches provider request;
- language retry preserves preset;
- registration page exists;
- accounts mode registration/login/logout works;
- local mode remains usable without registration;
- admin navigation exposes Providers/Models/Routing/Users/System only after admin auth.
